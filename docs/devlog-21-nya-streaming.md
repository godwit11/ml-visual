# devlog-21 · Nya 改成流式输出（逐字上屏）

日期：2026-09-15
起因：用户问「对话流畅度是不是有问题？是不是输出 token 设少了？」

---

## 1. 先确认不是 token 的问题

用站点的**真实系统提示词**直接打 MiniMax：

| 指标 | 实测值 | 含义 |
|---|---|---|
| `finish_reason` | `stop` | 正常说完，**不是** `length`（被硬截断才是） |
| `completion_tokens` | 88 / 上限 800 | 用了 11% |

⇒ `max_completion_tokens = 800` 绰绰有余，回答是完整的。
**真因：项目没做流式输出** —— 前端 `await res.json()` 拿到完整 JSON 才整段渲染，
那两秒里屏幕上一个字都没有，只有「···」。

---

## 2. 设计决策（改动前想清楚的几件事）

### 2.1 帧格式用 NDJSON，不用 SSE

```
{"t":"正文增量"}
{"done":true,"finish":"stop"}
{"error":"EMPTY_REPLY","message":"..."}
```

- SSE 的 `data:` **遇到换行必须拆成多条 `data:` 行**，正文里每个换行都要先拆再拼；
  NDJSON 的 JSON 字符串里换行天生就是 `\n` 转义，**按行切天然安全**。
- 代价：不是浏览器原生格式，不能用 `EventSource` —— 但 `EventSource` 只支持 GET，
  我们本来就要 POST 带请求体，用不上。
- 判据：响应头 `Content-Type: application/x-ndjson`。
  **前端靠它分流**：`x-ndjson` = 逐字正文；`json` = 一条完整消息（含错误）。

### 2.2 流式与否由**请求方**决定，不是"一律流式"

服务端默认仍回一次性 JSON，只有请求体带 `stream: true` 才走流。
理由：`check-server-path.mjs`、`nya-smoke.mjs` 这些自动化检查都挂在
"一个完整对象"上，为了新特性把它们全推翻重写，收益为零（它们不在乎首字延迟）。

### 2.3 错误必须分层，因为**开始吐流之后就改不了状态码了**

```
连不上 / 上游非 2xx / 没配密钥   → 还来得及 ⇒ JSON + 502/503（前端走原有错误气泡）
流跑到一半断了                  → 已上屏的字照常保留（那是真实回答的一部分）
一个字都没吐出来                → 在流末尾补一条 error 帧
```

所以 `handleChat` 里流式分流的**位置**很关键：必须放在两道失败闸门**之后**。

---

## 3. 改了四处

| 文件 | 改动 |
|---|---|
| `api/handler.ts` | 新增 `streamChat()` + `makeThinkingFilter()`；`wantStream` 开关；上游 payload 加 `stream: true` |
| `vite.config.ts` | 中间件从 `arrayBuffer()` 整体读改成**边收边写** + `flushHeaders()` |
| `src/core/nya.ts` | `readNyaStream()` 解析 NDJSON；空气泡逐字填；滚动用 rAF 节流 |
| `scripts/tests/nya-panel.js` · `scripts/check-server-path.mjs` | 假后端改吐流；各加一组断言 |

### 两个容易漏的细节

1. **`X-Accel-Buffering: no` + `Cache-Control: no-transform` 不是可选的** ——
   反向代理默认"攒够一块再转发"，一攒就把流式的意义全攒没了。
2. **中间件必须 `res.flushHeaders()`** —— Node 默认在第一次 `write()` 时才发响应头，
   而流式下第一次 write 要等上游第一个 token。实测修之前"响应头 2.22s 到"，
   和首字是同一时刻；修之后响应头 0.50~1.16s、首字 0.86~1.28s，能分出先后了。

---

## 4. 🔴 这一轮最值得记的：**测试自己可以是空的**

### 4.1 现象

新加的断言「跨包切断的 JSON 行能拼回来」全绿。按项目铁律做**反证** ——
故意把前端 `TextDecoder(..., {stream:true})` 的选项去掉，**测试照样全绿**。
连着修了两轮（加大分块间隔、加"分包真的发生了"的前提校验）**还是全绿**。

差一点就得出"这个选项没用"的错误结论。

### 4.2 根因：**切割点算错了**

我用 Python 的 `json.dumps(..., ensure_ascii=False)` 算字节偏移，
**它会在 `:` 后面加空格**（`{"t": "前半句"}`）；而前端的 `JSON.stringify`
不加空格（`{"t":"前半句"}`）。于是"切在第 12 字节"在 JS 里正好落在
**字符边界**上，第一块解码出来是完整的 `{"t":"前半句`[sic] ——
`{stream:true}` 写不写，**表现完全一样**。

插桩打出每块字节数才看清：

```
"12|{\"t\":\"前半"     ← 第 12 字节 = 6(前缀) + 3(前) + 3(半)，正好切在字符边界
"6|句\"}\n"
```

改成第 **11** 字节（落在"半"的三个字节中间）之后，反证立刻变红：

```
❌ 跨包切断的 JSON 行能拼回来（含被切成两半的汉字）  ← "前��句后半句"
```

### 4.3 顺手加的一条**前提校验**（这条最值钱）

```js
const firstChunkDecoded = new TextDecoder().decode(line1.slice(0, CUT))
check('（前提）分包的第一块真的切在多字节字符中间',
      firstChunkDecoded.includes('\uFFFD'), ...)
```

**没有它，那条分包断言随时可能退化成"什么都没验"** —— 而且它不会报错、
不会变红，只会安静地一直绿。这跟 `check-nya-state` 那类"最坏失败方式是不报错"
的检查是同一类问题。

### 4.4 服务端那侧的反证也一样

第一版的假上游是**一帧一帧顺着喂**的，每个 chunk 都和行边界对齐 ——
所以"没写残行缓冲"的反证照样全绿。把某一帧**切在 JSON 中间**之后，
反证立刻红掉两条：

```
❌ 流式：跨包切断的 SSE 能被拼回来          ← "这就是一句话\n\n答案："
❌ 流式：正常结束会给出 done 帧和 finish_reason  ← {"done":true,"finish":"UNKNOWN"}
```

**⇒ 造"分包"时，切点必须落在被切对象的内部，而且要有断言证明它真的落在内部。**

## 5. 实测：收益**取决于回答长度**（诚实版）

### 5.1 先修正一个错误结论

改之前我做过一次"非流式 2.59s vs 流式 TTFT 0.90s，快 2.9 倍"的测量，
并写进了记忆。**那是单次采样的噪音**，不成立。

### 5.2 交替采样（走完整链路，各 4 次）

```
流式：首字可读 1.18s   全部收完 1.48s   正文 43 字
非流式：首字可读 = 全部收完 1.25s        正文 48 字
⇒ 缩短 0.07s（6%）
```

**4 次流式里 3 次上游只吐了 1 帧**（`[51]`、`[47]`、`[32]` —— 整段一次性到）。

### 5.3 但长回答完全是另一回事

| 场景 | 非流式首字 | 流式首字 | 帧数 | 改善 |
|---|---|---|---|---|
| 短回答（46 字，站点常态） | 1.25s | 1.18s | 2 | 几乎无感 |
| **长回答（1441 字）** | **9.01s** | **1.77s** | 23 | **5.1 倍** |
| **长回答（1513 字）** | **6.47s** | **0.60s** | 23 | **10.8 倍** |

**上游的行为是：回答越长，分帧越细。** 短回答攒成 1~3 帧一次性发；
1441 字那次分成 23 帧、每帧约 40~100 字、每 0.3s 一帧。

### 5.4 结论

- 站点现在要求 Nya"两三句话"，所以**日常收益很小**；
- 但学生真的困惑、需要展开讲的时候（或者哪天放宽了"两三句话"的约束），
  收益从"锦上添花"直接变成"必需" —— 9 秒空等 vs 1.8 秒开始读；
- 而且这套基础设施是**更多能力的地基**（停止生成、重试、边写边读）。

---

## 6. 为什么**没有**做"打字机效果"

上游一次给 40~100 字，理论上可以用定时器一个字一个字吐出来，看着更像"在说话"。
**不做**，因为那等于**为了好看而故意拖延信息**：1441 字按每字 30ms 要 43 秒。
我们要的是尽快把真实的字交到学生眼前，不是表演。

---

## 7. 已知局限

- **`makeThinkingFilter` 的标签过滤不跨 chunk 缓冲** —— 如果 `<think` 被网络切成两半会漏。
  真正的防线是 `thinking: disabled` + `reasoning_split`；这一层只是廉价兜底。
  为它加缓冲会让**每个字**都多等一个 chunk，不划算。
- **中途断流不报错**，只保留已收到的文字。这是有意的（那半段是真实回答的一部分）。
- 上游帧粒度由服务商决定，我们能做的只是"收到就上屏"。
